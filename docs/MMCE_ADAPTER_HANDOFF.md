# MMCE Adapter Integration Contract

Implementation now exists in `foundation/content/mmce` and `MmcePonderPlugin`;
the pure geometry/budget tests pass. Full Gradle build is root-owned.

- `MmcePonderPlugin.refreshMachineIndex()` refreshes only registered machine metadata.
- `MmcePonderPlugin.clearPreviewCache()` releases bounded immutable preview snapshots.
- Root may call that static method from client world unload. It is now implemented.
- Calls must remain on the client main thread, excluding integrated-server unload
  callbacks. The adapter enforces its owner thread.
- `MmcePonderPlugin.getSceneSnapshot(PonderScene)` returns the snapshot associated
  with an already compiled scene, using weak scene keys. This is intended for
  persistent material/layer panels without any new compilation.
- `registerScenes()` refreshes machine metadata after MMCE registration, without building
  patterns, tiles, or recipes. `FMLLoadCompleteEvent -> PonderIndex.reload()` is appropriate.
- Calling `PonderIndex.reload()` explicitly refreshes definitions and invalidates cached previews.
- No client tick or world-load hook is needed. No world or server references are retained.
- UI-facing snapshots and material groups are available from `MmceMachineIndex`.
- No core API edit is required: scenes use a dedicated empty schematic and record read-only
  block/NBT events, not another demonstration's geometry.

The machine parser removes the controller at relative `(0,0,0)`. The adapter must add
the controller from the actual registration maps, not infer an item registry suffix.
Generic unbound controller items must not be mapped to every machine. A machine-specific
blueprint NBT binding provides an unambiguous fallback.

## Controller Preview Safety

`DetachedPonderWorld` rejects native MMCE controller Tiles before querying Tile
support, construction, or NBT deserialization. `MmcePreviewSafety` checks the
actual loaded superclass hierarchy for
`hellfirepvp.modularmachinery.common.block.BlockController`; this includes
`BlockFactoryController` and addon subclasses without guessing registry names
or requiring MMCE classes to be present.

This boundary is intentional. In the installed MMCE 2.3.2, controller
`readMachineNBT` with no machine/rotation calls `resetMachine(true)`, which can
enqueue a global synchronous task. Its normal custom-model TESR also submits
work to the global deferred controller render manager. A detached World alone
does not isolate either path. The adapter neither invokes these controller
paths nor clears MMCE's global queues.

Ordinary block structure is still displayed. Machine descriptors and their
derived snapshots explicitly note that controller special models are not yet
shown; those models require a dedicated read-only renderer. This is not an
acceptance claim for arbitrary third-party Tiles or renderers.

Focused verification on 2026-10-10: `MmcePreviewSafetyTest` (five tests) and
`PreviewIsolationSourceTest` (five tests) passed via standalone Java 8-targeted
compilation and JUnit. The runner is
`verification/mmce-safety/RunMmceSafetyTests.java`. These tests cover superclass
matching, optional-dependency absence, and the source-level callback boundary;
they do not instantiate a native Forge controller or prove rendering acceptance.

Hot reload is a separate known gap: after changing/reloading MMCE or
CraftTweaker definitions, run `/ponder reload` to refresh descriptors and
invalidate snapshots. MMCE's registry reload does not currently trigger this
invalidation automatically. No automatic reload hook is added by this fix.

## Controlled Installer

The installer is available at `validation/tools/Install-TestChapter.ps1`.
It has not been run against `client-sandbox` or the original Minecraft instance.
Only root should schedule that installation after stopping the sandbox.

```powershell
.\validation\tools\Install-TestChapter.ps1 -SandboxName <prepared-sandbox-name>
```

The sandbox name is mandatory. The script accepts only direct children of the
fixed `C:\CODEX\Ponder-MMCE-Integration\validation` root. It requires the existing
`validation-manifest.json` with matching sandbox path, schema, PonderValidator
identity, expected main class, and an unchanged-source flag. It rejects reparse
points, hardlinks, inaccessible Java command lines, and a running target Java
process. Paths to the original instance cannot be passed as the target.

`FtbChapterMergePlan.java` uses the actual installed FTB 1.12 SNBT parser/writer.
It validates the fixture manifest, deterministic UIDs, quest/task identities,
component links, safety fields, and collisions with existing SNBT IDs.
The chapter index preserves existing order and other NBT fields. Existing
chapters must match semantically for idempotence; differing contents fail.
The standalone fixture `file.snbt` is never copied or overwritten.

Existing quest-link entries, metadata, and enabled/autoLinkItems policies are
preserved. Identical normalized IDs are retained without duplicate entries;
different targets fail. A missing link configuration receives the explicit
fixture defaults. If existing linking is disabled, installation does not
silently enable it; the transaction records that preserved policy.

Transactions are under `validation/transactions/<sandbox>-<time>-<nonce>`:

- `plan.json` records inputs, hashes, ordered chapters, and allowed changes.
- `transaction.json` records identity hashes, each applied/rolled-back operation,
  protected `file.snbt`, and final status.
- `staged` retains candidate output; `backup` retains every replaced file.
- `planner.log` retains parser and conflict diagnostics.

The script checks the input snapshot before commit, backs up changed files,
and uses atomic file replacement. Handled failures restore prior bytes and
remove only newly created files/empty directories. Unexpected concurrent edits
or a Java process appearing during failure recovery prevent destructive
rollback and leave `rollback_incomplete` evidence. Unfinished transactions block
another installation until reviewed; there is no automatic crash recovery.

Supporting files are restricted to `validation/tools`; no launcher, README,
or production-source edit was made for this assignment. The only executable
started by installer tests is a short-lived, self-exiting Java guard probe,
not Minecraft.

`Test-InstallTestChapter.ps1` passes **21 offline regression cases**. These
include merging a copied fixture root, preserving non-JSON SNBT index fields,
byte-idempotent repetition, absent and equivalent links, conflicting normalized
links and UIDs, duplicate JSON keys, invalid indexes/manifests/paths, junctions,
hardlinks, a live target JVM, unfinished transactions, and two injected failure
points. One failure is before replacing the index; the other is after replacing
the index, proving that existing bytes are restored from backup as well as
removing new files.

`validation/installer-test-results-20261010152518.json`.
All generated test sandboxes are named `install-test-*`, directly under
`validation`, and are retained with their transaction evidence. The successful
